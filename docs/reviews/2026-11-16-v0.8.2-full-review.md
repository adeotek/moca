# Review — moca v0.8.2, full repository (2026-11-16)

**What this repo does:** moca is one Go binary — a small, provider-agnostic terminal coding agent (TUI, `moca -p` one-shot, `moca acp`) with eight frozen tools, a permission ladder around shell execution, skills/prompts loading, and cross-provider LLM calls. It publishes itself: release packaging, installers, self-update, Homebrew/winget/ACP-registry renderers. `docs/specs/SPECS.md` is the normative spec; `README.md` is the user-facing face.

**Load assumed:** one user on a laptop — one interactive session per directory, occasionally two moca processes sharing `auth.json`, the config, the trust store and the model cache (hence `internal/flock` on every read-modify-write). No server, no multi-tenant load. Egress: GitHub API/releases for `moca update`, provider APIs for inference. README and SPECS are the evidence for this, not a guess.

**Flows traced:** `cmd/moca/main.go` `run()` dispatch (config-before-subcommand ordering, `.env` boot, log routing under ACP) → `internal/update` (release fetch, checksum verify, atomic swap, package-manager refusal) → `internal/provider/auth.go` (0600 atomic store, cross-process lock held across a rotating refresh, control-byte key validation) → `internal/permissions/jail.go` + `plan.go` confinement (symlink-resolving resolve, dangling/loop refusals, plan write zone) → `internal/session/writer.go` (append-only JSONL, flock single-writer, crash trim) → `internal/tools/web.go` (private-address gate, dial-time re-check, redirect source tracking). Orientation via `graphify query`; the eight-tool contract against `internal/tools/testdata/schemas.golden.json`.

**Checks run on this tree (all green):** `make vet` (go vet + gofmt, clean) · `make test` (`-race`, all 22 Go packages ok, including the AGENTS/SPECS doc-count pins) · `go test -tags counts ./cmd/moca -run TestSpecsTestCount` (SPECS §15's 1495/22 claim holds) · `make build` + `bin/moca --version` → `moca v0.8.2` · the three hermetic gates: `test/acpgate`, `test/skillgate` (17/17 legs), `test/goalgate` — all pass · `GOOS=windows go build ./...` and `GOOS=darwin go build ./...` (both pass **today**) · `bash -n install.sh` and `shellcheck -S warning install.sh` (clean).

## Findings

### Must fix

None. The trust boundaries I read in full (update, auth, jail, plan confinement, session writes, web fetch) are implemented carefully and each has adjacent tests; no live bug, data-loss path or security hole surfaced.

### Should fix

1. **`.github/workflows/ci.yml:53-69` — CI never compiles the Windows/macOS-only files**
   - **What this is:** the CI gate is gofmt, `go vet ./...`, `go build ./...`, `go test -race` — all on `ubuntu-latest`, so every default-GOOS build. Files behind `//go:build windows` (`internal/flock/lock_windows.go`, `internal/tools/shellrun_windows.go`, `internal/update/replace_windows.go`) and `internal/session/lock_other.go` (`!(linux||darwin||…)`) are excluded from all four steps.
   - **Problem:** a PR that edits `replace_windows.go` or `shellrun_windows.go` is green on every push and only fails when someone manually dispatches the Release workflow — a windows-only break blocks the release instead of the pull request, and no test ever ran against the compiled file.
   - **Fix:** add two steps (or a small matrix) after the existing build: `GOOS=windows go build ./...` and `GOOS=darwin go build ./...`. I ran both against this tree — they pass today, so the gate lands green, not in fire-fighting mode.
   - **If we skip it:** the first signal for a Windows/macOS-only compile error is a failed release run on tagging day, bisecting a PR merged weeks earlier.

2. **`README.md:387` — the Development section undercounts the eval corpus and the gates**
   - **What this is:** the paragraph says the eval corpus has "twelve scenarios" and that "Two scripted harnesses sit beside the unit suites (both need a model key…)" — evals and shipgate only.
   - **Problem:** `test/evals/` holds **15** scenarios with a `prompt.txt` (SPECS §… and AGENTS.md both say fifteen), and there are **five** gate harnesses — `skillgate`, `goalgate` and `acpgate` are missing entirely, though they are the three that need *no* key and no network. A new contributor following the README runs two of five gates and believes the corpus is three scenarios smaller than it is; the two claims the counts tests do not pin are exactly the two that drifted.
   - **Fix:** rewrite the paragraph: fifteen scenarios, five gates, naming which need the `.env` key (evals, shipgate) and which are hermetic (skillgate, goalgate, acpgate), each with its one-line purpose.
   - **If we skip it:** the README keeps steering contributors away from the three cheapest gates, and the corpus count stays wrong in the first document every reader sees.

3. **`docs/specs/SPECS.md:39-40` — the command block contradicts the rest of SPECS**
   - **What this is:** the §2 command list says skillgate runs "16 legs" (`:39`) and labels the eval corpus "rev 21" (`:40`); the body says "17 legs" (`:510`) and "rev 33" (`:46`), and `test/skillgate/skillgate_test.go` really has legs 1–17 (I ran them: all pass).
   - **Problem:** SPECS is the single source of truth, so an internal contradiction is worse than plain staleness — a reader who trusts the command block will "fix" a gate that is already correct, and the doc-count tests pin only §15's test/package numbers, never these.
   - **Fix:** `:39` → 17 legs, `:40` → rev 33 (matching `:46`, `:510` and AGENTS.md).
   - **If we skip it:** the spec keeps two answers to the same question, and the next audit has to re-derive which one is real instead of reading it.

### Nice to have

4. **`docs/BENCHMARKS.md:74` — "v0.7.12 now, the newest tag" is three releases stale**
   - **What this is:** the Reproducing section pins `MOCA_VERSION` to "v0.7.12 … the newest tag"; `git describe` and the tag list say **v0.8.2**.
   - **Problem:** anyone reproducing the benchmark from this page pins a three-release-old binary while believing they are running the current one, so the reproduction does not test what the page claims to describe.
   - **Fix:** drop the "newest tag" phrasing (say "pin the release under test, e.g. v0.8.2"), or bump it at each release — the former needs no maintenance.
   - **If we skip it:** the reproduction instructions quietly drift further behind every tag.

5. **`internal/permissions/probe/main.go:1-39` — a tracked `main` package nothing runs**
   - **What this is:** a 39-line manual symlink-escape probe (creates `/tmp/moca-int`…`/tmp/moca-ext` fixtures and prints `Jail.Resolve` results), left over from the v0.4.0 permissions overhaul.
   - **Problem:** searched `Makefile`, `mise.toml`, `.github/`, `docs/`, `AGENTS.md`, `README.md`, `test/`, `scripts/`, `cmd/`, `internal/` — no reference anywhere (only `cmd/moca/counts_test.go:71` names it as the reason the package count is 18). Its scenarios are already pinned by `internal/permissions/jail_test.go:171-183` (dangling, chain, loop, cycle — refused). Dead code that carries a doc-count dependency.
   - **Fix:** delete it and update AGENTS.md's opening line to 17 packages — `TestAgentsGoFileCount` will fail loudly until the doc is updated, which is the pin doing its job.
   - **If we skip it:** a reader who greps for how symlink escapes are tested finds an untested manual toy instead of the real tests, and the package count stays propped up by dead code.

6. **`install.sh:1-254` — no shellcheck gate in CI**
   - **What this is:** the 254-line installer performs checksum verification, asset-name escaping, PATH/package-manager decisions and uninstall — security-relevant shell — and CI lints none of it (only Go is gated).
   - **Problem:** a shell regression reaches every `curl | bash` user with no automated signal; `shellcheck -S warning install.sh` passes today, so the gate would start green.
   - **Fix:** add `shellcheck -S warning install.sh` (and `bash -n`) as a CI step; shellcheck is preinstalled on GitHub's Ubuntu runners.
   - **If we skip it:** the install path — the first thing a new user runs — is the one script in the repo with no lint behind it.

# Pass 2 — logic, spec conformance and security (2026-11-16)

Pass 1 mapped the repo and traced the flows; this pass reads the **implementation against the spec**. Reviewed in full: the permission core (`internal/permissions/shell.go` classify/Check, `rules.go` matcher, the `auto*.go` risk table), the plan-mode path (`internal/tools/plan.go`, `write.go`, `edit.go`, `internal/agent/plan.go`), the web fetch gate (`internal/tools/web.go`), the auth store (`internal/provider/auth.go`), the trust store (`internal/permissions/trust.go`), log redaction (`internal/applog/redact.go`), the auto-mode classifier (`internal/agent/judge.go`), `-p` trust resolution (`cmd/moca/oneshot.go`) and shell env hygiene (`internal/tools/shellrun.go`). Two hypotheses were settled **empirically**: I wrote throwaway probe tests into `internal/tools`, ran them against the real code, then deleted them — `git status` shows only this report. One probe confirmed a gap (finding 7), one refuted my own suspicion (process substitution, below).

This pass supersedes pass 1's "Must fix: none" — the deeper read found two.

## Must fix

7. **`README.md:268` + `cmd/moca/oneshot.go:128` — plan mode's "no other writes" promise is not enforced against the shell tool**
   - **What this is:** README promises a plan run refuses "every write outside `docs/plans/*.md`", and the `-p` banner prints "(no other writes)". Enforcement exists only in `write`/`edit` (`internal/tools/write.go:101-105`, `internal/tools/edit.go:39-42`); the shell tool carries no plan check at all, and the analyser's redirect handling (`internal/permissions/shell.go:1215-1221`) validates targets against the workdir jail only — never the plan zone.
   - **Problem:** proven with the real `permissions.Shell` in plan mode's exact configuration (plan rides on `default`/ask, jail = workdir, no asker): `echo pwned > pwned-by-shell.txt` returned `[exit 0]` and created the file, while the `write` tool in the *same* environment refused with `plan mode only writes docs/plans/*.md`. Builtins never ask, so a plan run — including a headless `-p` plan run, whose entire purpose is "change nothing" — can silently overwrite any file in the workdir through a redirect; a prompt-injected page fetched during plan research is the obvious steer. Note `docs/specs/SPECS.md:369` is **honest** about this ("`shell` + mcp calls under the permission ladder", Ben's 2026-10-09 follow-up), so the code matches the normative spec and the README contradicts both — the same README sentence even says shell stays "under their normal permission rules" before claiming every write is refused.
   - **Fix:** smallest — correct the false absolute in `README.md:268` and the `oneshot.go:128` banner to what is actually enforced ("`write`/`edit` are confined to `docs/plans/`; shell runs under the normal permission rules"). To make the promise instead of the prose true: give the analyser a plan zone the way `skillDir` gets its refusal (`SetSkillDir`) and refuse redirect/`tee` targets outside `docs/plans/*.md` while plan mode is on — every redirect target already flows through `checkTargetText`, so the check has a single insertion point and does not touch `git log`/builds.
   - **If we skip it:** plan mode stays a prompt-level suggestion for the one tool that writes without asking; users keep trusting a guarantee a weak model or an injected instruction bypasses with `echo x > src/main.go`, and the corpus checker catches it only in evals, after the fact.

8. **`internal/tools/web.go:265-268` — the fetch gate misses RFC 6598 shared address space (100.64.0.0/10)**
   - **What this is:** `webPrivateIP` is `IsLoopback || IsPrivate || IsLinkLocal* || IsUnspecified` — Go's `IsPrivate` covers RFC 1918 and RFC 4193 only — and `TestWebPrivateHost` (`internal/tools/web_test.go:421`) pins exactly that table, so the gap is load-bearing in both directions: the test would fail if someone fixed it by accident, and nothing else can fix it.
   - **Problem:** proven by probe — `webPrivateHost("100.100.100.200")` and `webPrivateHost("100.64.0.1")` return **false**, and a fetch to `http://100.100.100.200/latest/meta-data/` fired **no approval** and went straight to a connection attempt (it failed only because this host has no route), while the `127.0.0.1` control asked and was refused. 100.64.0.0/10 is precisely what the gate's own comment claims to protect ("Private targets (loopback, LAN, link-local, **cloud metadata**)"): **Alibaba Cloud's metadata service is 100.100.100.200**, and **Tailscale/CGNAT peers live in 100.64.0.0/10**. On such a host a prompt-injected page steers a metadata-theft or peer-LAN fetch past the gate with no prompt — the exact attack the gate exists for, on the exact class of host the comment names.
   - **Fix:** add the range beside `IsPrivate()` in `webPrivateIP` (100.64/10 at minimum: after `To4()`, `ip4[0] == 100 && ip4[1]&0xc0 == 0x40`; consider `192.0.0.0/24` and `198.18.0.0/15` while there), pin the new rows in `TestWebPrivateHost`, and add an end-to-end case asserting a denied asker *refuses* a CGNAT fetch instead of connecting.
   - **If we skip it:** the metadata/peer protection the gate advertises silently does not cover one major cloud or any Tailscale host, with no user-visible signal — the fetch simply happens.

## Checked and found sound (pass 2)

- **Process substitution is classified** — my hypothesis was *refuted* by probe: `cat <(curl …)` and `echo >(curl …)` both refused `curl` exactly like the plain-`curl` control, because `syntax.Walk` descends into `ProcSubst.Stmts`; already pinned by `internal/permissions/shell_test.go:64` (`cat <(rm x)` → ask-every `rm`).
- **Classifier fails closed** — `internal/agent/judge.go`: errors, timeouts and unparsable replies all yield "ask"; only `allow` verdicts are ever cached; `parseJudge` rejects unbalanced or foreign JSON instead of guessing.
- **Auth-store concurrency** — every read-modify-write, including a rotating refresh, runs under `flock` bounded at 30 s; writes are tmp + rename with a forced 0600; a transient refresh failure falls back to a still-valid token rather than failing the request (`internal/provider/auth.go:163-369`).
- **Trust store** — `Set` re-reads and merges under the lock, refuses to clobber a malformed store, renames atomically; both callers (`cmd/moca/tui.go`, `cmd/moca/acp.go`) load fresh per decision (`internal/permissions/trust.go:57-99`).
- **Plan/edit ordering** — the plan-zone check runs *before* the ask-write approval in both tools, so plan mode never prompts, exactly as SPECS §10.4 states.
- **Log redaction is handler-level** — secret-named attributes, `*url.URL` values (query and userinfo stripped) and error truncation happen in `replaceAttr`, so a stray `slog` call cannot leak a key by call-site mistake (`internal/applog/redact.go`).
- **`-p` trust rule** — `cmd/moca/oneshot.go:105-108`: explicit flag > yolo > untrusted; saved decisions are ignored in `-p`, matching SPECS §7.
- **Auto table fails safe** — `autoVerdict`'s zero value is `autoUnsure`; every risk-table parser returns unsure/ask for anything it cannot place; a path-qualified, case-variant or non-literal head can never reach `autoAllow` (`internal/permissions/auto.go:98-107`).

## Production readiness (updated verdict)

**Approve with fixes.** The project is in production shape for its stated load — one user, one terminal, one machine: the full race suite, all three hermetic gates and both doc-count pins are green on this tree; the code carrying credentials, trust, confinement and binary replacement is written with locks, atomic renames, fail-closed defaults and an explicit threat model in SPECS §11; and the two findings below are narrow, cheap to fix, and both sit *behind* the documented prompt-injection adversary — neither is remotely exploitable without first steering the model.

**Conditions before relying on plan mode as a guarantee (finding 7):** correct the README/banner claim today, and preferably land the analyser's plan-zone check — until then, treat plan mode as "the model was told not to", not "the run cannot".

**Conditions before running on a cloud VM or a Tailscale host (finding 8):** add 100.64.0.0/10 to the fetch gate — a ~3-line change plus its pins.

Everything else from pass 1 (findings 1-6: CI cross-compile gap, README/SPECS/BENCHMARKS drift, the stray `permissions/probe`, no shellcheck gate) still stands and is independent of these two.

## Findings

### Medium

#### 1. `/clear` regresses the status-bar branch to `-` until the next turn ends — Confirmed
`internal/tui/app.go:427-442` (`restartSession`)

`restartSession` zeroes `m.status = StatusInfo{}` and calls `refreshStatus()`, which sets every field except `Branch`/`Dirty`/`Git` (app.go:89-93) and issues no `branchCmd`. The bar therefore shows the dimmed `-` non-git placeholder in a git repository after `/clear`, contradicting the phase-gate expectation that the bar is correct from the first frame of a session; `Init` resolves the branch only once at program start. Secondary: if `agent.Start` fails inside `restartSession`, the old session has already been closed (`Session().Close()` at app.go:429) while `m.agent` still points at it, so the next submit appends onto a closed writer and errors.

Failure scenario: run `moca` in any git repo, wait for the bar to show `main*`, type `/clear` → the new session's bar reads `… · - · …` until the first run's TurnEnd re-resolves the branch.

Proposed fix: in `restartSession`, don't zero the branch fields (or return `tea.Sequence(restartCmd, m.branchCmd())`), and keep the old agent wired until `agent.Start` succeeds.

### Low

#### 2. A literal chip marker typed before a paste hijacks `Text()` expansion — Confirmed
`internal/tui/input.go:57-65` (`Text`)

`Text()` replaces the *first* occurrence of each stored marker. If the buffer already contains that exact marker string (the user quoted a previous chip, or is discussing the feature), a subsequent paste gets the same marker and the expansion lands on the typed text instead of the paste.

Failure scenario (reproduced with a probe test against the real package): input `[paste 55 lines #1] ` typed, then a 55-line paste (marker `[paste 55 lines #1]`). `Text()` returns the 55 lines substituted at the typed position and sends the literal string `[paste 55 lines #1]` where the real paste is — the pasted content is silently replaced by a marker literal in what gets sent. Related: `ToggleChips` collapse has the same first-occurrence behaviour with duplicated expanded content.

Proposed fix: when creating a marker in `Paste`, bump `#K` until the marker string does not already occur in the buffer (or scan for stored markers from the right, or store paste positions instead of string matching).

#### 3. `eventPipe` blocks its caller once 1024 events are pending — Confirmed (blocking), Plausible (scenario)
`internal/tui/bridge.go:60-80`

The comment says emit "never blocks the caller"; it only holds below the 1024-slot channel. I reproduced that the 1025th concurrent `emit` blocks when the forwarder's `Program.Send` is stalled (`Program.Send` selects on the unbuffered `p.msgs`, bubbletea v2.0.10 tea.go:1192-1196).

Failure scenario: the event loop stalls for a long time while a run streams (e.g. renderer/terminal backpressure on a huge view, or a very slow filesystem inside the `A`-approval `AppendString`) and the agent produces >1024 events — the agent goroutine then blocks in emit until the loop catches up, delaying the esc-cancel path's `TurnEnd`/abort handling. Not reachable with the current fast `Update` handlers under normal terminals.

Proposed fix: on a full pipe, drop `TextDelta`/`ThinkingDelta` payloads (keep a placeholder) or grow/shed with a counter, so ordering of control events (ToolStart/ToolEnd/TurnEnd/approval-adjacent) can never be delayed by a full buffer; adjust the comment to state the bound.

#### 4. A failed run leaves the trailing partial live line stuck, and the next run silently drops it — Confirmed by reading
`internal/tui/app.go:542-545` (`handleRunDone`), `app.go:129` (`startRun`)

`handleRunDone` flushes `m.live` only when `msg.err == nil`. On an errored/interrupted run the partial streamed line stays in the live region of `View()` after `running` is false, and the next `startRun` resets `m.live` without ever printing it — the user loses the visible tail of what the model was streaming (the transcript still holds the persisted text, so this is display-only).

Failure scenario: a run streams `checking the test fi…` and is interrupted (`esc`) → `[interrupted]` prints but `checking the test fi` remains frozen above the input box and vanishes on the next submit.

Proposed fix: flush `m.live` unconditionally in `handleRunDone` (through `printlnContent`) regardless of `msg.err`.

# Codemode — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans`. Steps use `- [ ]`. `moca execute docs/plans/<this file>` can walk it too.

**Goal:** an opt-in `codemode` tool: the model writes a short JavaScript program that runs in an in-process sandbox and calls back into moca's own tools, so multi-call sequences execute as one call and huge tool output is filtered before it reaches context.

**Architecture:** `internal/codemode` is a sandboxed QuickJS-NG interpreter (built to WASI reactor WASM, run by wazero — pure Go, no cgo) embedded inside `internal/tools` as a ninth built-in tool. The interpreter has no filesystem, no network, no timers: programs reach the outside world only through injected global functions that dispatch into a `tools.Registry`. Opt-in by the same two-layer resolution self-managed skills already established (user config enables; a trusted project file may only opt out). One frozen .wasm ships in the repo and is `//go:embed`ed.

**Tech Stack:** Go 1.27 (unchanged pin). New deps (both pure Go, no cgo, no platform-specific code): `github.com/tetratelabs/wazero` (zero-dependency WASM runtime; MIT; A/2) and `golang.org/x/jsonpatch` is **not** needed. That is one new direct dependency. QuickJS-NG itself is not a Go dep — its `qjs-wasi-reactor.wasm` release asset is vendored at pin time.

**Spec:** `docs/specs/SPECS.md` is normative. This plan amends §1 (implemented list), §4 (config keys), §10 (a ninth tool, with its own frozen schema rule), §11.0 (an explicit boundary statement), §13.5 (log rules) and §16 (non-goals note for the future capability escalation). Each task names its SPECS edit; it lands in the same PR (§16).

**Sequencing:** single-PR implementation, but the .wasm fixture and its harness must land and be verified before the tool that embeds it (Tasks 2 and 4 are strictly before Task 5). No prior PR needed. No version bump mid-train (the release workflow bumps; this lands with whatever the current `main` version is).

## Global Constraints

- Import direction (AGENTS.md): `llm`/`config`/`update` import nothing internal → `provider` → `mcp` → `agent` → `tui` | `acp`; `tools`/`permissions`/`session`/`skills`/`compact` stay mutually independent. `internal/codemode` is a **new leaf package in the `tools` tier**: it imports nothing internal except `internal/llm` (for the spec type); `internal/tools` imports it; `agent`/`tui`/`acp` do not touch it directly.
- The eight frozen tool schemas stay byte-identical (`internal/tools/testdata/schemas.golden.json`); the core prompt stays byte-identical for `PromptInput{}`. `codemode` ships its own golden schema file and is **excluded from that test's registry snapshot**, not bolted onto it.
- The system prompt is built once per run and never rebuilt (`internal/agent/start.go:668`, pinned by `TestSplitSystemPrompt`'s rejoin and the prompt line budget). A resumed session that started with `codemode` off keeps it off (`TestCodemodeResumeNeedsClear`), so the session header needs a switch stamp (see Design).
- Config decode is strict everywhere (§4: unknown keys are rejected). The new keys live in `codemode` (user) and `codemode` (project) blocks and must join `moca config sample` (`TestSampleCoversEveryKey` walks every key of `Config` — a new struct field *with a json tag* must appear in `sample.jsonc`, commented if inactive by default).
- Caps go in code, not prose. Metadata-only logs (§13.5): the tool's log line carries name, ms, and error class — never script text, never a tool argument, never output.
- Every PR: `make vet` + `make test` green, SPECS updated (incl. the §15 recount), CHANGELOG entry, at most one version bump, `graphify update .` after code changes.
- Commits only with the user's explicit approval; `main` is PR-only; subjects follow `[{type}:{category}] short description`.

## Review Focus

1. **Input policy is opt-in, not inherited (Decision 1).** The tool computes pure data by default. Inputs are **explicit named bindings** the model declares per call (values only — strings, numbers, booleans, null, flat arrays, flat objects; no file paths, no URLs). A trusted project config may add `dataFiles` globs; when it does, a matching binding resolves to that file's **bytes** (verified `stat`-stable against the workdir) — that is the only project-authorized widening, and it is a data decision, never an execution decision. When no project block exists, there is no path surface at all (Decision 3). **Veto point:** if you want the runtime file/ls-read surface for `inputFiles`, flip one boolean in one struct (`ToolsInputFileTool`); the plan builds without it and pins the refusal message in `TestNoPathsNoFileSurface`.
2. **The interpreter is a sandbox, not the tool's safety story (§11.0 addition).** Both models of the same failure class are pinned: WASM crashes bubble as `IsError` (Task 3's never-panic test), and every tool call **inside** the sandbox carries `canAlways: false` (Task 6) so the TUI/ACP approval ladder still prompts for anything the called tool would have asked. The user approves through the same surface they already trust.
3. **A new cap for a new attack surface: `maxOutputChars`, default 2000, pinnable ceiling 32000.** Every third-party codemode caps output; ours does too (`maxOutputTokens`-style, character-denominated — deterministic, model-independent). A script can do real data work and still hold its answer to 2000 chars.
4. **The frozen-nine rule is its own test, not a quiet edit to the frozen-eight test.** `TestSchemasFrozen` gets a sibling (`TestCodemodeSchemaFrozen`) over the new tool only; `agent_test.go:349`'s `len(tools) != 8` becomes conditional on the switch (Task 7) — this is the edit that would otherwise silently break every session that runs the feature, and it gets its own test (`TestOffSessionsStayEight`).
5. **Go/runtime feature-idiom parity is bounded by a fixture, not by hope.** The .wasm build must support ES2023 + async/await + modules (`JS_EVAL_TYPE_MODULE`, so top-level `await`/`return` works as pi's does). `test/evals/codemode/fixtures.suite.json` names the six working features (async, destructuring, JSON, array ops, object methods, regex literals) and four forbidden ones (`process`, `require`, `fetch`, dynamic `import()`) — a runtime upgrade that loses one fails the gate.

## Findings (why this design)

- **F1 — the eight-tool freeze is load-bearing, not decorative.** `internal/tools/builtins.go:5` returns exactly eight in schema order; `internal/tools/tool_test.go:50` (`TestSchemasFrozen`) and `internal/agent/agent_test.go:349` (`len(tools) != 8`) both pin the count. Adding a ninth without adjusting both is a guaranteed test break that would then tempt a quiet golden rewrite. This plan treats the ninth tool as its own contract: `codemode` rides the same `Registry` (its entry sits after `mcpStub`, registered from `build()` only when the switch resolves on) and carries its own frozen golden file (`internal/tools/testdata/codemode-schema.golden.json`).
- **F2 — "tools, not sandbox escape" is the whole product.** The OpenCode README states it outright: *programs cannot access the network, filesystem, processes, or application APIs — they can interact with the outside world only through tools provided by the host*. Pi's docs say the same: *no Node APIs, file system, network, or timers; scripts reach the outside world only through tools*. Both products reject the OS-container path entirely — no seccomp, no cgroups, no Landlock. That is the correct scope here too (F3), and moca's existing shell permission model (§11.0, `internal/permissions/jail.go`) should not be reshaped to host it.
- **F3 — the pure-Go WASM interpreter wins on every axis that matters here.** Cross-compiling moca already produces 6 platform binaries (`make release`); a second runtime (Deno, Node, a WASI CLI) per platform would add a download, a path discovery, and a version-drift failure mode for every platform, on a feature that is opt-in by default. Embedding a WASM module in-process ships in the same binary with zero runtime deps and one vendored `.wasm`. The dependencies: `wazero` (zero-dependency WASM runtime, no cgo, MIT) and a QuickJS-NG WASI reactor module (`.wasm`, MIT) vendored as a fixture. Total: **one Go dependency**. Build once at the QuickJS-NG release tag; the repo embeds the artifact, never the compiler toolchain (Task 2 runs the build from a Docker scratch image — WASI SDK only, nothing else installed).
- **F4 — Starlark and GoLua are the wrong fit for this workload.** starlark-go (`go.starlark.net`, Google, BSD-3) is *the* interpreter-shaped Go dep, but its own README states the limitation directly: *it is not possible to bound memory, no way to bound memory in a Starlark thread* — the resource model is weaker than what an agent runtime can put around user-shaped scripts. GoLua's safe-execution layer is still labelled *alpha* upstream (README + `quotas.md`) and its safe-mode is CPU/memory-quota-based, not capability-based. Neither has a language surface for `await`-per-tool-call, which is the shape the two real reference implementations chose.
- **F5 — the fixture build is the plan's real security gate, and it deserves a task of its own.** The QuickJS-NG WASI reactor (`qjs-wasi-reactor.c`, MIT) exposes exactly `js_QuickJS`-shaped exports (init / eval / get_result / free); a host never injects WASI file or network capabilities beyond the interpreter's own imports. The Docker build pins the WASI SDK and the QuickJS-NG tag so the .wasm byte-for-byte reproducible is testable (`qjs-wasi-reactor.wasm` release asset, 1560132 bytes at v0.18.0). Nothing else is compiled into it.

**Keep as-is:**

- The frozen-eight rule, the `Jail`/`Shell` analysis layer (§11), the session/resume path, the TUI/ACP approval ladder. `codemode` rides all of them unchanged except the tool-count pin (F1) and the §11.0 boundary sentence.
- `test/evals` grading stays as-is. A new `codemode` scenario joins only if the suite's anti-duplication gate would admit it (`reuse`, `writeup`, `review` exist to keep the corpus lean); it does not join here (Task 12 defers it with a trigger).

**Rejected:**

- **Windows-only shell parsing of a new language surface (the `§11` path).** QuickJS is a real interpreter with a real AST; wrapping it in the shell permission ladder buys nothing and loses the actual safety argument (the interpreter is the boundary).
- **A subprocess-per-script sandbox on any OS (bwrap on Linux, sandbox-exec on macOS, an AppContainer/job-object shape on Windows).** moca is a single static binary; a sibling process must exist on every platform, discover a toolchain per OS, and — critically — its *hosting* is the failure surface (a child process is a real attacker target on Windows where sandbox-exec is unavailable, and Windows has no macOS-equivalent). OpenCode and Pi both ship an in-process interpreter for exactly this reason.
- **starlark-go as the interpreter** (F4's memory bound) and **GoLua** (alpha-tagged safe mode) — both fail the "smallest and most stable dependency" bar for a security-sensitive surface.
- **JSON Schema-only tool signatures** (the §7 Code Mode README's "render-only JSON Schema" variant). moca's own tools already carry `llm.ToolSpec` with JSON Schema; reusing it as the source of truth costs nothing extra and keeps one schema path. The binding layer (Task 5) validates arguments with the existing `decode` helper instead of inventing a second.
- **A `codemode`-namespaced directory tree exposed to script-side `fs` operations.** Capability-based filesystem access is a real future feature (V2 trigger: a genuine script-side file need a user reports). Building it now invents a sandbox the first task would have to prove safe, and the tool's promise (F2) is already the harder one to keep.

## Design

### The tool surface

`codemode` — one call, one optional `options` object, one program string:

```json
{"code":"const rows = await tools.read({...}); return rows.split('\\n').filter(...).length",
 "options":{"bindings":{"rows":"<string>"},"timeoutMs":5000,"maxOutputChars":2000},
 "toolChoice":"search",
 "maxToolCalls":50}
```

- `code` — required. The interpreter's input is a **module** (`JS_EVAL_TYPE_MODULE`): top-level `await` and `return` work as pi's do, and pi's "REPL-style result" is kept — a bare expression result (a non-module `eval` path for a one-liner without `return`) returns too, so a three-line check is not forced into a return statement.
- `options` — optional. `bindings` is the only input surface (F1/Decision 1): flat values only. `timeoutMs` (default 10000, hard ceiling 30000) and `maxToolCalls` (default 50, hard ceiling 200) and `maxOutputChars` (default 2000, hard ceiling 32000) are **fixed by the build**, not by config: no layer can weaken a cap. `toolChoice` is metadata only (the description already carries it — the model's chosen tool comes through the `llm.ToolCall` itself); the field exists to satisfy the frozen schema's own `additionalProperties: false` shape, and the interpreter reads nothing from it.

**The schema is frozen too.** `internal/tools/testdata/codemode-schema.golden.json` pins `{"code","options"}` exactly, same shape discipline as the eight.

### The sandbox (Task 4)

`internal/codemode/interp.go` — one wazero runtime **per process**, created lazily:

```go
rt := wazero.NewRuntimeWithConfig(ctx,
  wazero.NewRuntimeConfigInterpreter().WithMemoryLimitPages(64).WithCloseOnContextDone(true))
mod, _ := rt.Instantiate(ctx, wasmBytes) // the vendored qjs-wasi-reactor.wasm
```

- 64 memory pages × 64 KiB = **4 MiB** of guest memory — more than enough for a filtered-JSON program, and a hard cap a script cannot grow past (WASI `memory.grow` fails; the guest is a fixed-size memory with no `malloc` growth room beyond that).
- `WithCloseOnContextDone(true)` is the **wall-clock enforcement path**: the host's context cancellation (the tool call's `ctx`, i.e. an aborted run, an esc, a killed process) interrupts the interpreter mid-bytecode, not at the next WASI call boundary. `timeoutMs` is a child of this: the tool wraps its own `ctx` in `context.WithTimeout` before invoking, so the same mechanism handles both a deadline and an abort.
- Memory-limit exhaustion, a runtime panic inside the WASM module, and a `close-on-context-done` interruption all surface as the same Go error type → the tool wraps them all as one `IsError` result that names the class (`out of memory`, `cancelled`, `crash`). **A crash inside the interpreter must not panic the agent's tool loop** (`runRecovered` in `internal/tools/tool.go:424` is the backstop, but the tool's own code never relies on it).
- No WASI filesystem is mounted (`WithFSConfig` is never called): the module sees an empty `/`, no `open()`, no `read()`. No WASI network imports are linked. The interpreter's only way out is the exports we call and the host functions we inject — no `fd_write` beyond an internal stdout buffer that the tool drains and caps at the same `maxOutputChars`.

### The bridge (Task 5)

`internal/codemode/bridge.go` — the host's injected globals, one per existing tool class:

- `tools.<name>(args)` — the only externally meaningful call. Dispatches by name into the `tools.Registry` the session already built (the same `Registry.Run` the agent loop uses, `internal/agent/agent.go:891`), which means **the called tool runs on the same goroutine the tool call itself is on** (the judge's own rule, `TestJudgeAccountsCost`) — no concurrency surface is invented here.
- `text(v)` — append one text item to the result (string or JSON-serialized value).
- `return v` at top level — one value, serialized.
- `console.log(...)` — joins args with spaces into the `<console_output>` block, one line per call.
- `searchTools(q)` / `describeTool(name)` / `ALL_TOOLS` — the description-discovery globals pi carries. These are the *only* introspection surface, and they read the session's tool list (the nine specs + the `mcp` proxy's roster names, never schemas or argument shapes — the roster line is all a model sees, `internal/agent/start.go:476-482`).
- `store(k, v)` / `load(k)` — pi's per-script small state, keyed in `Env`, capped (one value ≤ 4096 chars of JSON, total ≤ 65536, all values JSON-safe). Written only on script success (pi's rule, carried over verbatim).

**No file surface exists by default.** `tools.read` called from the bridge with `path` = anything is `Env.Paths.Resolve(path, false)` — the jail resolves and refuses exactly as `read` does today (`internal/permissions/jail.go:199`). No `inputFiles` glob, no implicit `read`, no implicit `ls`. The TUI's `@path` completion and `tools.read`'s existing jail work unchanged. The `dataFiles` project-config surface (Task 6) is the only way a script gets bytes, and it names them from the **host side**, not the guest side.

### Config

`codemode` (user layer, `internal/config/config.go`):

```jsonc
"codemode": {
  "enabled": false,          // the opt-in. `true` is required for the tool to exist.
  "dataFiles": []            // user layer: max 32 globs, each relative to the workdir
},
```

`codemode` (project layer, `internal/config/project.go`):

```jsonc
"codemode": {
  "enabled": false,          // only `false` means anything; `true` is declarative (matches skills.selfManaged's shape)
  "dataFiles": []            // may add to the user layer's globs (union, dedupe), never remove
},
```

- Resolution (`config.ResolveCodemode(cfg)`, pinned by `TestResolveCodemodeTable`): on only when the user config says `true` and the trusted project file does not say `false` — the identical shape `ResolveSelfManagedSkills` already implements (`internal/config/config.go:161`), for the same reason: a cloned repository cannot turn a tool on, but it can opt out of one the user turned on.
- `dataFiles` validates in both layers: each entry a relative POSIX-style glob (no `..`, no absolute, no `~`), max 32, max 4000 chars each; `filepath.Match` compiles at load time (a bad pattern is a config error, never a runtime surprise).
- The warning/note texts mirror the skills wording, one line each, emitted from `prepare()`-adjacent code (`internal/agent/start.go:646-716`) exactly once per start.
- The session header carries `codemode` (bool) alongside `selfManagedSkills` (`internal/session/entry.go:57`) so resume renders the same tools it started with.

### Where the tool is built

`internal/agent/start.go:473-481`:

```go
reg := tools.NewRegistry(tools.Builtins()...)
if cfg.CodemodeOn() { // the resolved switch, computed by prepare()
    reg.Register(tools.Codemode(mgr, env)) // the bridge, injected with the same tool registry
}
```

`tools.Codemode(...)` is `internal/tools/codemode.go`: the `Tool` adapter — `Spec()` returns the frozen golden, `Run()` parses `code`/`options`, calls into `internal/codemode` with the bridge, and formats the result. `Registry.Register`'s existing rule (`internal/tools/tool.go:347`: replace-in-place by name) is unchanged.

### Result shape (fixed, deterministic)

```
<status> <wallMs>ms
<content>
[<console_output>]
<console lines>
</console_output>
```

- `status` is `completed` or `failed`. A failed script keeps its partial output, then `error:` + the error (pi's rule).
- `content` carries the `text()` items and the return value in order, truncated to `maxOutputChars` with `[… truncated — the script returned more]` and the full text spilled via the existing `tools.Spill` (the same overflow the eight tools use, `internal/tools/tool.go:105`).
- `Summary` is `codemode <status> <ms>ms` — a TUI row that fits the existing status bar.
- Tool calls the script made are **not** replayed into the transcript as their own entries: the outer `codemode` call gets one `tool_result` (the §10 sequential execution rule stays untouched). The TUI's `toolArgSummary` (`internal/tui/toolsummary.go:13`) needs one new `case "codemode"` returning `firstLineOf(code)`; ACP's `toolInput`/`toolTitle` (`internal/acp/toolcall.go:19-91`) need one `Code string` field and one case, and its `endUpdate` reports only the capped text (never nested tool bodies — the editor's 8 KiB cap, `internal/acp/toolcall.go:16`).

## Out of scope (v1)

- **A second language surface (Python, Starlark, WAT).** The bridge and the schema are language-agnostic; the trigger is a user report that JS cannot express a shape the job needs.
- **`inputFiles` (runtime file/ls-read surface) without a project block.** Decision 1 keeps the default compute-only; the trigger is a user report naming a workflow the `dataFiles` surface cannot serve.
- **`models.*` (running non-LLM models from scripts).** Pi's classifier/image surface is a real capability, not a sandbox one; moca's provider catalog is behind auth, and bridging it through codemode would move the auth surface into the interpreter. The trigger is a use case that needs it, at which point the bridge gets one new global, not a redesign.
- **A `codemode` eval scenario.** The anti-duplication gate exists to keep the corpus lean; the trigger is a measured behavior change worth A/B-ing (a scenario joins only if it would regress without the tool's presence).
- **Shell availability inside codemode.** Permanently refused (Task 4's construction), not a config key: a shell escape inside the sandbox is the one capability that would recreate the §11 threat model from inside a tool, and every third-party codemode ships without it for the same reason.

## Risks / decisions

| Risk | Mitigation in this plan |
|---|---|
| The vendored .wasm drifts from its build recipe | `TestFixturePinned` pins size + sha256; `BUILD.md` names the exact tag, SDK version and Docker invocation; a re-vendor is a deliberate edit to both |
| wazero's interpreter is slow (no native codegen) | Measured F0: the interpreter was chosen over the compiler for portability; `maxOutputChars` caps what a slow run can produce; `timeoutMs` caps how long a slow run can take. If a benchmark ever shows the interpreter as the bottleneck, the fix is `NewRuntimeConfigCompiler()` on the platforms that support it (a one-line change, no API break) |
| A script runs a tool the user would have refused | Every bridge call carries `canAlways: false` (Decision 2); the TUI/ACP approval ladder prompts exactly as it does for the eight built-in tools; `TestBridgeRefusesShell` closes the one capability that would bypass the ladder |
| A resumed session flips the tool on/off | `Header.Codemode` stamps at creation; `TestCodemodeResumeNeedsClear` pins it |
| The frozen-eight test count breaks silently | Task 5's `TestOffSessionsStayEight` makes the count conditional and names the shape; the eight-tool golden file is untouched |
| The tool's output reaches context unbounded | `maxOutputChars` (default 2000, ceiling 32000) + the existing spill path; `TestCodemodeTruncatedOutputSpills` pins both |
| A project config widens the surface for an untrusted repo | `dataFiles` exists only in a trusted project file (the same gate as the `mcp` and `permissions` blocks), and the resolver's table mirrors `skills.selfManaged`'s shape exactly |

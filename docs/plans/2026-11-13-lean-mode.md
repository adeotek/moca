**Goal:** Make "the smallest change that fully solves the task" an **operable procedure** in moca's system prompt instead of a preference, and make the size of what the agent writes a **measured number** in the eval corpus — so the claim "leaner" is falsifiable instead of felt. Ship three new built-in commands (`/review`, `/audit`, `/debt`) that reuse the existing built-in-skill mechanism, with zero new tools, zero new config keys and no new mechanism.

**Architecture:** Instruments first (task 1): the eval corpus gains deterministic diff-size metrics, recorded per session and reported by `evalstats` beside tokens and cost. Only then does the prompt change (task 2), because without the instrument the ladder cannot be judged. The `shortcut:` marker and the two review skills (tasks 3–4) ride the built-in-skill path that already exists (`internal/skills/builtin/`, `go:embed`, `/name` dispatch). Tasks 5–6 turn the ladder's two central bets into checkers — that an existing helper is reused rather than re-implemented, and that a requested explanation is not truncated — so both are gated, not asserted. Task 7 is the release.

**Tech Stack:** Go 1.27.4 (stdlib only; no new module dependencies), the bash eval harness (`test/evals/run.sh`), `evalstats`, `python3` for the checker helpers (already a dependency of `feature/check.sh`).

**Spec:** `docs/specs/SPECS.md` is normative. This plan amends **§2** (eval corpus metrics and scenarios), **§3.5** (`/help` and slash-command resolution), **§12** (built-in skills), **§14** (the system prompt's working-style contract), **§15** (release entry and test count). Each task names its sections, and the edit lands in the same PR (SPECS §16).

**Version:** this train is **v0.9.0**, one bump for the whole release, several PRs sharing it (AGENTS.md). A minor bump is the call because the release's headline is a *behavior contract change for every run*, not a fix — the same distinction that made v0.7.0 (self-managed skills) and v0.8.0 (`/goal`) minor while v0.7.10 (two new providers) was a patch. There is no version constant to edit: `Makefile:12` stamps `git describe --tags`, so the bump is the tag chosen at dispatch.

## Global Constraints

- **The prompt is a replacement, not an addition.** `internal/agent/system-prompt.md` is 41 lines / 5 370 B today and `prompt_test.go:54` fails above 60 newlines ("core prompt must stay ~40 lines"). Task 2 lands at 42 lines (≤ 43: one bullet out, two in; 43 is the ratchet's headroom): the ladder *replaces* the "Keep changes minimal … Don't add unrequested features" bullet and folds the reuse clause out of "Orient first". The two replacement bullets are a measured ~1 060 chars ≈ 260–300 tokens — that is the whole train's prompt budget, spent once per session in the cached head; any further prompt growth in this train is a plan failure, not a tuning opportunity. (Ponytail's own thesis applied to itself: deletion beats addition.)
- **One prompt edit, one cache reset.** `SplitSystemPrompt` (`internal/agent/prompt.go:185`) puts the whole of `system-prompt.md` in the cached head, so every byte of task 2 invalidates the prefix cache of every existing user, once. Task 2 is the train's **only** edit to that file — the `shortcut:` grammar rides inside it rather than as a later addition.
- **No new tools, no schema change.** The eight frozen specs and `internal/tools/testdata/schemas.golden.json` stay byte-identical. `/review`, `/audit` and `/debt` are built-in *skills* (prompt bodies the agent follows with the existing tools), not tools.
- **No new config keys.** No `lean: lite|full|ultra`. A knob before the default is measured is the thing this plan exists to avoid; the trigger for revisiting it is recorded in Findings (F6).
- **Size is a measurement, never a gate.** The new metrics are recorded with `pass: true` semantics — no `check.sh` reads them, no scenario passes or fails on its line count. This is the discipline that keeps a size number from contaminating a pass rate (ponytail's `benchmarks/loc.js` does the same, for the same reason).
- Import direction and package independence per AGENTS.md. Nothing here touches `llm`, `provider` or `mcp`.
- Logs carry metadata only (SPECS §13.5). No prompt, file content, command text or secret.
- **Every SPECS.md or README.md edit re-copies `internal/skills/builtin/self-knowledge/references/{specs.md,readme.md}` in the same commit** — `TestSelfKnowledgeReferencesAreByteIdentical` pins them byte-identical to the docs, so every task in this train fails `make test` until the copy rides along.
- Every PR: `make vet` and `make test` green, SPECS updated, `graphify update .` after code changes. Commits only with the user's explicit approval. Branch `chore/<slug>`; `main` is PR-only. Commit subjects in the house form `[feat:core] …` / `[chore:evals] …`.
- **Do not let the release number be decided per PR.** Every SPECS §15 entry in this train says **v0.9.0**, and the last PR collapses them into one section (the v0.8.0 entry records doing exactly that).

## Review Focus

Five inputs are implied by the work but not exercised by the obvious tests. Each gets a pin in its owning task.

1. **A run that commits its own work.** The size metric must measure the fixture commit → final tree, not `HEAD..worktree`: an agent that runs `git commit` would otherwise report zero lines changed. Owner: task 1 (`TestDiffSizeAcrossAnAgentCommit` in the run.sh selftest).
2. **A skill name colliding with a built-in command.** `/review` is new; a user's `~/.config/moca/prompts/review.md` must still win, because prompt templates are matched before skills (`internal/tui/commands.go:88` vs `:93`). Owner: task 4 (`TestAUserTemplateShadowsABuiltInCommandSkill`).
3. **`/debt` in a tree with no markers, and with markers that name no trigger.** The empty case must say so in one line, and a `shortcut:` that names no revisit trigger must be tagged, not silently listed — a silent deferral is the failure mode the command exists for. Owner: task 3. What is *pinnable* is the body carrying both the `no-trigger` tag and the exact empty-case string (`TestDebtSkillCarriesTheTagAndTheEmptyCase`, a body-content assertion, not a model test); actual compliance is a human read of one run against a scratch tree, recorded in the PR — a checker that greps a skill's *body* and calls it behaviour is the kind of green light this plan exists to avoid.
4. **The prompt ladder versus the verification and progress nudges.** The ladder says "act on what you know"; §14's progress nudge (rev 29) says "start implementing". They must not contradict, and the ladder must not license cutting the verification step. Owner: task 2, reviewed in the same edit; the nudge texts are unchanged.
5. **A resumed session written before this release.** Its stored system prompt has no ladder; the `# Project skills you maintain` block and the nudge set are unchanged. Resuming must not re-render or re-write the prompt. Owner: task 2 (`TestResumeKeepsTheStoredPromptWithoutTheLadder` — the existing built-once invariant, re-pinned against the new text).

## Findings (why these tasks)

Evidence comes from `DietrichGebert/ponytail` (v5.3.3, read at `216` files) and from this tree at `403fc1f`.

- **F1: The prompt states a preference where it needs a procedure.** Ponytail's core is not "write less code" — it is an *ordered ladder*, "take the first option that fully works": does it need to exist → already in this codebase → standard library or platform → an installed dependency → one readable line → the minimum. moca's equivalent is one bullet, `system-prompt.md:26`: "Keep changes minimal and in the style of the surrounding code. Don't add unrequested features." A preference can be satisfied by a nod; a ladder forces a check before writing. This is the single highest-leverage difference in the repo.
- **F2: Their claim is measured, and ours cannot be.** Ponytail publishes lines-of-code at 47% of a no-skill baseline with the same agent, and "98% of risky logic ships with a test" against 68% without — 39 tasks, 5 runs each, geometric mean of per-task medians. `test/evals/evalstats/main.go:43` (`Metrics`) carries steps, tokens, cache attribution, residency, cost and seconds — and **no size field at all**. `test/evals/vague/check.sh` asserts behaviour only: a 200-line solution and a 20-line solution both pass. Until a number exists, every leanness change is unarguable.
- **F3: Their observation that a test clause needs to be *explicit*.** Ponytail's ladder is bounded by "Never cut: validation at trust boundaries, error handling that prevents data loss, security, accessibility" plus "new non-trivial logic leaves one small test behind, trivial changes need none". Without the bound, "be lazy" reads as "drop the checks" — and their benchmark exists partly because an earlier version did exactly that. This is why task 2 must ship both halves in one edit, and why `feature/check.sh` (already requiring a `func Test…json`) is the precedent for task 6.
- **F4: A deferral with no revisit trigger rots.** Ponytail's `shortcut: <the limit>, <when to upgrade>` marker plus `/ponytail-debt` exists because "later" becomes "never" without a greppable artifact, and their debt command explicitly tags markers that name no upgrade path. moca already has the right instinct in `internal/skills` (hygiene, prune, "delete it when it is wrong") but nothing equivalent for code-level deferrals.
- **F5: Review structure beats review coverage.** Their `/ponytail-review` was rebuilt around a fixed finding shape — bold title with `file:lines`, then *What this is / Problem / Fix / If we skip it* — plus the breadth rule "read the code the change touches, not just the diff; a change can break code it does not touch". moca has no review command at all (`BuiltinCommands`, `internal/tui/commands.go:36`) and no shipped review skill (`internal/skills/builtin/` holds `create-command`, `self-configure`, `self-knowledge`), so users get an unranked wall of observations instead.
- **F6: Their intensity levels are the part not to copy.** `lite|full|ultra` exists because a global prompt has no other escape hatch. moca builds the prompt once per run and stores it, has `/effort` for the model and `/mode` for permissions, and would need a new config key plus strict-decode handling for a knob whose default nobody has measured. **Trigger for revisiting:** a reproducing case in the eval corpus or a user report where the ladder withholds something that was actually needed. Until then: no key.
- **F7: Their plumbing is a portability tax moca does not pay.** 248 KB of hooks and twenty adapter manifests exist because those hosts have no first-class system prompt — Claude Code needs a `SessionStart` hook and a flag file to say "you are lazy now", OpenCode a `chat.system.transform` plugin. moca embeds its prompt, builds it once and caches it. Nothing in that integration layer applies; only the prompt, the marker and the finding shape do.

**Keep as-is** (they already work, and this plan does not touch them): the eight frozen tools, the append-only request invariant, the plan-mode envelope, the verification and progress nudges, the self-managed-skills contract, the four-bullet answer discipline in §14's "working style" (the ladder extends it; it does not replace it).

**Rejected:**
- Intensity levels / a `lean` config key (F6).
- Porting hooks, a status band, or the local analytics board: moca's status bar already carries model, context percent, in/out tokens and cost (`internal/tui/status.go`), and `/cost` prints the detail. Re-implementing them would be the over-engineering this plan is about.
- promptfoo and regex-graded model answers: the corpus's real-repo fixtures with executable `check.sh` are strictly stronger, and `--selftest` already proves each checker fails its fixture and passes `testdata/reference`.
- A ninth tool for debt harvesting: `/debt` is a prompt over `search` + `read`.
- Rewriting the whole working-style section: the newline cap and the "~40 lines" intent make this a surgical substitution.

- [ ] **Step 3: Implement the fields and the flags.** `Metrics` gains `Added, Removed, Files, NewFiles int` with `json:"added,omitempty"` and friends (additive, so old rows in `results/*.jsonl` still parse and read as zero). `main`'s flag set gains `-added -removed -files -newfiles` (no `CollectInput`: the flags set the fields on the row `main` builds from `Collect(entries)`, and Step 6's real rows are that mapping's end-to-end pin). `Summarize` gains a `lines (mean ± sd)` column and a `new files` column; `-compare` treats `Churn()` as one more ratio metric beside tokens and cost, through the existing stratified bootstrap. - [ ] **Step 4: Compute the diff in `run.sh`, read-only.** In `fresh_repo`, after the fixture commit, record `BASE=$(git -C "$2" rev-parse HEAD)` and write it beside the workdir (`"$2.base"`), not inside it — the workdir is what `check.sh` inspects and what the leak scan walks. In `one()`, after `check.sh` has run, compute:

```bash
size_of() { # size_of <workdir> <base> -> "added removed files newfiles"
  local w="$1" base="$2" a=0 d=0 f=0 nf=0
  # tracked modifications and deletions (a file the agent committed is no
  # longer in the worktree diff, which is why base is the fixture commit)
  while read -r add del path; do
    [ "$add" = "-" ] && continue
    a=$((a + add)); d=$((d + del)); f=$((f + 1))
  done < <(git -C "$w" diff --numstat "$base" -- . ':!.moca' 2>/dev/null)
  # files the fixture never had: --numstat does not show them untracked;
  # .moca/ is excluded on both pathspecs — it holds the agent's project
  # resources (an allow-always config, a self-managed skill, a saved
  # command), not code, and counting it inflates the metric on exactly the
  # scenarios that write the most
  while read -r path; do
    nf=$((nf + 1)); f=$((f + 1)); a=$((a + $(wc -l < "$w/$path")))
  done < <(git -C "$w" ls-files --others --exclude-standard -- . ':!.moca' 2>/dev/null)
  echo "$a $d $f $nf"
}
```

  Read-only by construction: `--numstat` and `ls-files --others` mutate neither the index nor the worktree, so a checker that inspects `git status` still sees what the agent left.

  **The harness stages nothing into the workdir** — `run.sh:171` points `XDG_CONFIG_HOME`, `XDG_DATA_HOME` and `XDG_STATE_HOME` elsewhere and passes `--config` from `$EVALS`. The **agent** is what writes there: `.moca/config.jsonc` from an allow-always answer, `.moca/skills/*` from the self-managed-skills contract (the `skills` and `skills-inject` scenarios build exactly that on purpose), `.moca/prompts/*` from `create-command`. Those are project resources, not code — hence the `:!.moca` pathspec on both walks, in code and not in prose. Without it `NewFiles` reads high precisely where the corpus's most interesting scenarios write the most, and the metric would be wrong where it matters. Pass the four numbers to `"$STATS"` as `-added -removed -files -newfiles`.

- [ ] **Step 1: Write `/review`.**

```markdown
---
name: review
description: Review the current changes like the senior dev who gets paged when they break — bugs, risk, scale, missing tests, speed, and what to cut.
argument-hint: "[uncommitted|staged|branch|pr <url>|files…]"
---
Review the change; change no code. The user names the target in plain words; with none, review the uncommitted change, or the last commit when the tree is clean. Get the diff with `shell` (`git diff`, `git diff --staged`, `git diff <base>...HEAD`, `git log -1 -p`).

Read first, review second. For every changed function, read its callers — a change can break code it does not touch — and the tests that cover it. Read the project instructions and the README for the load the project expects (one user, or many processes).

Then look, in this order:
1. Bugs: wrong result, crash, a missed edge case, a caller broken by the change, a fix applied in one caller while the shared function stays wrong.
2. Risk: security holes, data loss, an authorization check that moved.
3. Scale: check-then-write races, work every process repeats, memory that only grows, a query per item, O(n²) on the input the README implies.
4. Risky logic with no test — logic that has a branch, a loop, a parser, money or security in it.
5. Speed: big problems as problems, small ones as suggestions.
6. Lean: dead code, a helper the repo already has, stdlib or a platform feature instead of a new dependency, an abstraction with one implementation, near-copies to merge, one function doing several unrelated jobs to split. Never split by line count.

Every finding needs a concrete case — the input that triggers it, or the caller that breaks. Re-read the lines before you write the finding; a plausible-sounding finding that does not survive a re-read is worse than no finding. A `shortcut:` comment that names its limit is a decision, not a finding. Propose the smallest fix, prefer deleting code, never add a layer. No style taste, no vague worries.

Reply shape: start with `What this change does:` in two or three sentences, then the load you assumed. Then numbered findings, grouped `Must fix` / `Should fix` / `Nice to have`, most important first. Each finding: a bold title with `file:lines`, then exactly four bullets — `What this is` / `Problem` / `Fix` / `If we skip it`. End with `Verdict:`, then `Lean: -N lines possible.` when the lean findings allow a count, and `Not checked:` naming anything that mattered and you could not check. Nothing found: `Looks good. Ship.`
```

- [ ] **Step 2: Write `check.sh` with three arms — correct output, reuse, no duplication.**

```bash
#!/usr/bin/env bash
# pass: tests green, the two known sizes render exactly as internal/human does,
# AND the formatting was reused rather than re-implemented. Arm 1 pins the
# RENDERING (a raw-bytes duplicate prints "1536 B" and fails here); arm 2
# catches a duplicate that keeps the IEC spelling; arm 3 only catches a
# deleted helper (report already calls it).
set -u
go test ./... >/dev/null 2>&1 || { echo "tests fail"; exit 1; }
tmp=$(mktemp -d); trap 'rm -rf "$tmp"' EXIT
head -c 1536    /dev/zero > "$tmp/tiny.bin"
head -c 2097152 /dev/zero > "$tmp/big.bin"
out=$(go run . list --sizes "$tmp" 2>&1) || { echo "--sizes fails: $out"; exit 1; }
grep -q '1\.5 KiB' <<<"$out" || { echo "tiny.bin not rendered as 1.5 KiB: $out"; exit 1; }
grep -q '2\.0 MiB' <<<"$out" || { echo "big.bin not rendered as 2.0 MiB: $out"; exit 1; }
# reuse: the unit spelling lives in one package (a new helper, an inlined
# switch, a literal "KiB" in main.go — the bloat this scenario exists to
# catch); the whole internal/human package is exempt, its test asserts the
# literals by design
bad=$(grep -rl 'KiB\|MiB' --include='*.go' . | grep -v '^./internal/human/' || true)
[ -z "$bad" ] || { echo "re-implemented size formatting in: $bad"; exit 1; }
grep -rq 'human\.Bytes(' ./cmd ./internal --include='*.go' || { echo "existing helper not called"; exit 1; }
```

Pinning `1.5 KiB` and `2.0 MiB` closes that: only a formatter that matches `human.Bytes`'s own contract produces them, which is the thing being measured. Arm 2 then covers the one case arm 1 cannot — a duplicate that reproduces the spelling with different arithmetic. Arm 3 is not the reuse gate: `report` already calls `human.Bytes`, so it can only catch a deleted helper.

#!/usr/bin/env bash

set -u
go test ./... >/dev/null 2>&1 || { echo "tests fail"; exit 1; }
[ -n "${SESSION:-}" ] || { echo "no session (selftest arm)"; exit 1; }

## Open items this plan knowingly leaves open

1. **A `lean` intensity switch.** Trigger: a reproducing over-cut in the corpus or a user report where the ladder withheld something the task needed (F6). The fix would be a config key plus a rendered variant of the ladder section — never a second prompt.
2. **Judge-based graders for the write-up and review shapes.** The crude prose thresholds in task 6 and the four-bullet read in task 4 are human-checked in the PR. A judge call in a *pass rule* would import exactly the sampling noise the corpus spends its effort removing; it belongs in a separate, clearly-labelled measurement if it is ever wanted.
3. **`reuse %` as a per-run TUI figure.** Ponytail surfaces it in its band. moca's `/cost` shows tokens and cost; a `files touched / new files` line there is cheap and additive, but it needs a diff against the run's first write, not the fixture commit, and that is a session-model question this release does not need to answer.

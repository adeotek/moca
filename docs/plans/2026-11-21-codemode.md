# codemode — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans`. Steps use `- [ ]`.

**Goal:** an opt-in `codemode` tool: the model writes one JavaScript program that loops over moca's own tools and returns only its result, so a 40-file sweep costs one round trip instead of forty.

**Architecture:** a second process, not a second language runtime in the agent. `internal/codemode` (new leaf package) embeds **goja** (pure-Go ECMAScript 5.1 + most ES6) and exposes exactly two host objects — `tools.<name>(args)` and `console.log`. The VM has no filesystem, no network, no timers, no `require`, and no moca state. Every external effect is a **request over a pipe to the parent process**, which executes it through the existing `tools.Registry` — the same jail, permission ladder, classifier, skill guard, plan zone and snapshots every other call uses. The VM runs in a disposable child (`moca codemode-worker`) so a runaway script, an OOM or a catastrophic regex is killed by the process group instead of wedging the agent. No OS sandbox, no cgo, no new platform matrix.

**Tech Stack:** Go 1.27.4 (pinned), stdlib + **one new dependency: `github.com/dop251/goja`** (MIT, pure Go, no cgo — the release matrix in `.github/workflows/release.yml` stays six cross-compiled binaries).

**Spec:** `docs/specs/SPECS.md` is normative. This plan amends §2 (package list + import direction), §3 (the internal subcommand), §4 (one config key), §10 (the tool and its opt-in registration), §11 (the approval-budget rule), §14 (one prompt slot), §15 (counts).

**Sequencing:** v0.8.4 is the last tag (`65ba195`/`81fc50d` on main); no open PR blocks this. PR A is self-contained; PR B is data-gated and does not block A.

## Global Constraints

- Import direction (AGENTS.md): `codemode` is a **leaf** (stdlib + goja only). `tools` may import it (the `mcp` proxy precedent: `mcp` also imports `tools`/`config`/`llm`); `agent` wires it. Nothing else.
- **The default tool set stays byte-identical.** `Builtins()` keeps returning eight (`internal/tools/builtins.go:5`), `TestSchemasFrozen` (`internal/tools/tool_test.go:50`) stays green untouched, and `Builtins()` is *not* the place a ninth tool appears. `codemode` is registered conditionally in `agent.start` beside the existing conditional `mcp` proxy registration (`internal/agent/start.go:473-482`). Consequence: a user who never enables it sees the same 8 schemas, the same prompt bytes and the same cache prefix as today.
- The core prompt stays byte-identical for `PromptInput{}`: the one new line rides a `{{codemode}}` slot that renders **empty** when off — the exact mechanism `{{rtk}}` already uses (`internal/agent/prompt.go:79-104`), pinned both ways by `TestPromptTemplateSlots` (`internal/agent/prompt_test.go:196`), which gains one name.
- Caps are code, not prose: every limit in the table below is a constant with a test that trips it. No config knobs beyond `codemode.enabled`.
- `internal/tools.Env` is single-goroutine by contract (§11.0: "the tools read Env from Run's goroutine"). The worker design exists so this stays true: the parent handles the child's requests **on the run goroutine**, strict request/response, no second goroutine touching `Env`.
- Metadata-only logging (§13.5): `slog.Debug("codemode", calls, duration, error_kind)` — never the script text, never a nested tool's arguments.
- Every PR: `make vet` + `make test` green, SPECS updated (§15 recount with the established `=== RUN` method), CHANGELOG entry, no version bump per PR, `graphify update .` after code changes. Commits only with explicit approval; `main` is PR-only.

## Review Focus

**R1 — The sandbox is the process boundary plus the tool boundary, and nothing else.** The VM cannot reach the OS (no fs/net/exec/timers in goja's surface — we expose two objects), and the child cannot reach moca's memory (separate process, minimal env). Every side effect is a `tools.X` call executed by the parent, so the blast radius is *identical to the model calling that tool directly* — codemode adds no egress path, no write path, no privilege. A script that a prompt injection steers into `tools.web` or `tools.shell` hits the same private-host gate and the same ladder. **Owner:** Task 1 + Task 3, pinned by `TestScriptCannotReachHost` (a script touching `require`, `process`, `fetch`, `setTimeout`, `globalThis.console` beyond the host object fails) and `TestNestedCallGoesThroughTheLadder` (a nested `rm` produces a `Question` exactly as a direct call does). **Settled:** no OS jail in v1. A bwrap/Landlock path is a Windows hole and a §16 non-goal change, and the child + tool boundary already bounds the blast radius to "what the model could do anyway". Revisit only if the threat model ever includes a hostile local user — that is the trigger, and it changes the worker's spawn code.

**R2 — A runaway script must not be able to take the agent with it.** Three failure modes the VM cannot bound by itself: unbounded allocation (goja has no heap cap), a catastrophic-backtracking regex (`regexp2` runs inside one Go call — `vm.Interrupt()` cannot preempt it), and a plain infinite loop. The child process answers all three: the child self-interrupts at the deadline and the parent kills the process group at deadline+2 s. **Owner:** Task 2, pinned by `TestHardKillBeatsAWedgedVM` (a script parked in `for(;;)` and one parked in `/(a+)+$/` both return within the bound, and the agent's next tool call still works). **Settled (Q3):** the child process, with the hard kill. In-process is the cheaper build and the honest cost is a session that can hang forever on a regex or an allocation storm.

**R3 — One approval per nested call, ten per script, then only free calls.** Nested calls keep their own `Question`s (the ladder is unchanged), which means a loop can machine-gun the user's attention; that is the failure mode an opt-in script feature introduces. The parent counts *approval-requiring* calls and refuses the 11th with a model-facing message naming the budget. **Owner:** Task 3, pinned by `TestApprovalBudget` (11 ask-tier calls → the 11th returns `refused: …approval budget…`; free calls still run afterwards). **Rejected alternative:** pre-approving the whole script ("run this script? y/N") — a script's effects are the calls it makes, and nobody audits a program at a glance. The budget is the compromise.

**R4 — Adoption is the real risk, and it is measurable.** A tool the model never chooses is dead weight. 79.5 % of moca's tool-call turns emit exactly one call (measured, F1), so round-trip collapse is the win, but only on fan-out tasks — which the current eval corpus does not contain (median run = 10 calls). PR B ships the scenario that decides whether the feature earns attention: `test/evals/sweep`, read via `evalstats -compare` against a labeled baseline in `BASELINE.md`. **Owner:** Task 10 (data-gated; PR B does not block A).

**R5 — The script API is a contract that costs a cache reset per edit.** `tools.x(args)` → `{ok, text, summary}`, `console.log`, `return`. No `store()`, no `searchTools()`, no `image()`, no async: a synchronous call is a synchronous tool call, which is exactly what moca's loop already does. The description is pinned in its own golden file (`internal/tools/testdata/codemode.golden.json`) so it cannot drift silently, and every wording change is one cached-prefix reset for enabled users. **Owner:** Task 4. **Deferred with a trigger:** async/`Promise.all` would buy parallel nested calls but needs a mutex over `Env` (single-goroutine contract) — the trigger is a measured latency complaint on N≥20 files.

**R6 — Where the feature lives in config: user enables, project may only disable.** Exactly `ResolveSelfManagedSkills`'s shape (`internal/config/config.go:125-148`): a project `true` is declarative and warns; a project `false` opts the repo out. A cloned repo must not be able to hand itself a new execution surface — the same reason `ProjectConfig` refuses `defaultMode: yolo`, `allow: "*"`, `permissions.auto.model` and `approve: ["*"]` (`internal/config/project.go:70-90`). **Owner:** Task 5, pinned by `TestResolveCodemodeTable` and `TestProjectCannotEnableCodemode`.

## Decisions (settled with Ben, 2026-11-21)

1. **Language: goja.** One dependency (`github.com/dop251/goja`), leaf-only import, no cgo, release matrix unchanged.
2. **The default contract stays: eight tools.** `codemode` is registered only when `codemode.enabled` is true (the `mcp` proxy precedent at `start.go:481`); `Builtins()`, `schemas.golden.json` and the default prompt bytes are untouched. Joining `Builtins()` would be a frozen-schema event for every user — deferred, not rejected, and decided only by the PR B numbers.
3. **Child process: yes.** `moca codemode-worker` + request/response over stdio + hard kill at deadline+2 s (R2).
4. **Which tools a script may call: every registered tool except `codemode`.** The gates are the ladder's, unchanged; mutations are visible in the summary's per-tool call counts; plan mode remains the read-only lever (its write zone refuses `write`/`edit` outside `docs/plans` and shell redirects outside the zone).
5. **`-p`/headless: allow codemode.** Nested asks are denied by the absent asker — the refusal inside the script is the model's feedback.
6. **Name: `codemode` everywhere** — tool, config key, docs, activity rows.

## Findings (why this design)

**F1 — moca's loop is one call per turn; that is what codemode collapses.** Across the four newest eval labels (`results/v090b-base`, `v090b-ladder`, `v081rel-base`, `v080-base`; 159 runs, 1,389 assistant turns carrying tool calls): **1,105 turns (79.5 %) carry exactly one call**, 244 carry two, 34 three, 6 four. Median run: 10 steps, 10 calls. So a 20-file sweep is ~20 round trips today and 2 with codemode.

**F2 — the per-round-trip price is measured, not assumed.** On `v090b-base` (39 runs): median `cacheRead` 39,168 tokens, median `input` 11,064, median 10 steps ⇒ **~3,884 cache-read tokens and ~$0.00035 per step** on the eval model, ~1.4 s/step. Fan-out is not rare: 11/39 `v090b-base` runs and 15/39 `v090b-ladder` runs contain at least one tool with **≥5 calls**. `read` is 21–45 % of tool-result residency across labels — the token a sweep pays 40 times.

**F3 — the corpus does not contain the task shape that pays.** Median task = 10 calls, small synthetic repos; the largest observed single-message fan-out is 4 calls. codemode's payoff case (dozens of homogeneous calls whose results are filtered) appears zero times. That is why PR B exists and why "on by default" must not be decided in PR A.

**F4 — goja is the only engine that fits the release contract.** Pi uses QuickJS (cgo); OpenCode wrote its own interpreter (`psychoscript`, a separate repo). moca ships six cross-compiled binaries with `CGO_ENABLED=0` and has never owned an interpreter. goja: pure Go, MIT, ES5.1 + most ES6 (Map/Set/Promise/regexp), `Runtime.Interrupt()` for the deadline, single-goroutine per `Runtime` (matches `Env`'s contract), min Go 1.26. Cost: one dependency, ~2 MB of binary, and a VM with **no heap cap** — which is why the VM lives in a child process (R2).

**F5 — the freeze is about the default set, and conditional registration is already the pattern.** `start.go:473` builds `NewRegistry(Builtins()...)` and `:481` replaces the frozen `mcp` stub with the lazy proxy *only when servers are configured*. A ninth tool registered the same way is not a schema break: `TestSchemasFrozen` compares `Builtins()` only, and the prompt slot renders empty. Enabled users pay the one-time cache reset that any tool-block change costs; nobody else pays anything.

**F6 — Pi's and OpenCode's models do not transfer whole.**
- Pi: async function body, `tools.<name>` with structured outputs, `text()/image()`, `store()`, `models`, `searchTools`, `codemode.mode: on|only`, workers capped at 2. moca has no image/classifier models, no deferred tool catalog (only MCP, which has its own search inside the `mcp` schema), and no reason for `only` mode: eight declared tools cost ~1.5 K tokens of request block (eval `firstPrompt` 4,107 − `systemPromptTokens` 2,574), which is not worth hiding behind a script.
- OpenCode: "rather than sandboxing arbitrary JavaScript, only run the language features we implement" — the strongest statement of the philosophy, and the one argument for a bespoke interpreter. It also confirms the limits that matter (`timeoutMs`, `maxToolCalls`, `maxOutputBytes`) and the diagnostic-kinds shape, which moca adopts as a closed set of error prefixes.
- Both leave limits **unlimited by default**; moca ships safe defaults, because its threat model is the weak model's mistake, not an attacker's intent.

**Keep as-is:** the ladder, the jail, plan mode's write zone, the skill guard, snapshots, the read-before-write rule, the investigation protocol, the `mcp` proxy gating. codemode calls into them; it never re-implements them.

**Rejected:**
- **In-process VM (no child)** — cannot kill a wedged `regexp2` match or an allocation storm; the agent hangs or OOMs with no recovery. Cheaper by ~250 LOC and strictly worse (R2).
- **QuickJS via cgo** — breaks the six-platform static release contract; `CGO_ENABLED=0` is load-bearing.
- **Starlark (`go.starlark.net`)** — the better *bounds* story (hard step cap, `MaxAllocs`, no I/O by design), and the worse *adoption* story: the model writes this code, and its JS training data is orders of magnitude larger. Real risk with Starlark is a script that parses but does something subtly different; with JS the failure is a syntax error the model fixes in one turn. Revisit only if goja's resource residuals bite in practice.
- **wazero + a wasm-compiled interpreter** — real isolation and fuel-based interruption, at 10–30 MB embedded (or a supply-chain download for a feature most users leave off).
- **A `codemode` mode of the loop (Pi's `only`, all tool calls routed through scripts)** — collapses *every* round trip, which is the real prize, but rewrites the loop, the TUI, ACP and session replay. Out of scope with a trigger: the eval in PR B showing the tool-shaped version wins but is rarely chosen.
- **An MCP server that implements codemode (`moca codemode` over stdio, reached through the `mcp` proxy)** — would avoid the ninth tool, but a script must call *moca's* tools and an MCP server cannot call back into them; it would need its own tool implementation list, i.e. a second ladder. Dead end.
- **Per-script blanket approval ("run this script?")** — meaningless consent: the script's effects are the calls it makes, and the user cannot audit a program at a glance. Per-call approvals + the R3 budget is the honest version.
- **`store()` / cross-call state, `searchTools()`, `image()`, `models`, namespaces, suspend/resume, durable tools** — each exists in Pi/OpenCode because of a capability moca lacks or a scale moca has not reached. Triggers are in Out of scope.

## Design

### The script surface (everything the model may use)

```js
// the whole host API: tools.<name>(args) -> {ok, text, summary}, console.log, return
const hits = tools.search({ pattern: "DeprecatedCall", glob: "*.go" });
if (!hits.ok) return { error: hits.text };
const files = [...new Set(hits.text.split("\n").map(l => l.split(":")[0]))];
const out = [];
for (const f of files) {
  const r = tools.read({ path: f, limit: 200 });
  if (!r.ok) { console.log("skip " + f); continue; }
  out.push({ file: f, lines: r.text.split("\n").filter(l => l.includes("DeprecatedCall")).length });
}
return out.filter(x => x.lines > 0);
```

- `tools.<name>` exists for every **registered tool except `codemode`** (no recursion, like Pi). Unknown name → `{ok:false, text:"unknown tool …"}` from the parent, never a JS exception.
- A nested call returns `{ok, text, summary}` — the `tools.Result` fields — for **every** tool, success or refusal. No exceptions: one shape, and a per-file failure cannot kill the sweep. `text` is what the model would have seen, minus moca's model-facing hints (the parent's nested path skips hint decoration, keeps run-state bookkeeping).
- `return <value>`: JSON-serialised if not a string; `undefined` → `null`. `console.log(...)` accumulates log lines, streamed to the parent as they happen so a killed script keeps its output.
- No `require`, `process`, `fetch`, `setTimeout`, `import`, `eval` of host scope, no filesystem object of any kind. `Date`, `Math`, `JSON`, `Map`/`Set`, `RegExp`, `Array` methods are goja's standard built-ins and are allowed.

### Limits (constants, each with a test)

| Constant | Value | Enforced by | Failure text |
|---|---|---|---|
| `maxScriptBytes` | 64 KiB | parent (input decode) | `invalid arguments: script is N bytes (limit 65536)` |
| `defaultTimeout` / `maxTimeout` | 120 s / 300 s | child interrupt + parent hard kill at +2 s | `script timed out after Ns (killed)` |
| `maxToolCalls` | 500 | parent | `script stopped: 500 tool calls (limit)` |
| `maxApprovals` | 10 | parent | `refused: this script's approval budget (10) is exhausted — finish with calls that need no approval, or report back` |
| `maxOutput` | 12 KiB (chars) | parent; overflow reuses `tools.Spill` (`internal/tools/overflow.go:21`) | `[output saved to <path> — read it …]` |
| `maxLogLines` | 200 | parent | `[… N console lines omitted]` |
| `workerHeapSoftCap` | 512 MiB RSS | child self-watch (best effort) | `script stopped: memory` |
| `killGrace` | 2 s | parent | (kill, then the timeout text) |

### Parent ↔ worker protocol (one script = one child)

```
parent spawns: moca codemode-worker          (hidden; stdin/stdout pipes; env minimal; process group)
parent writes: {"script":"…","timeout_ms":120000}\n
child  writes: {"log":"…"}\n                 (0..n, streamed)
child  writes: {"call":"read","args":{…}}\n  ← blocking; parent executes on the run goroutine
parent writes: {"ok":true,"text":"…","summary":"…"}\n     (or ok:false with the refusal/error text)
child  writes: {"done":{"value":<json>,"calls":7,"elapsed_ms":412}}\n   (or {"failed":{"kind":"timeout","message":"…"}})
child exits; parent reaps. Any EOF before done → the failure text carries the calls already made.
```

`args` crosses as the model wrote it (JSON object), so a nested call is validated by the same decode path as a direct call. The child never learns a path, a workdir or a key: it has no fs, so it needs none. A nested call is **not undone** on failure (it already ran) — the result says so, like Pi.

### Tool result shape (what the model sees)

```
script ok — 7 calls (read×5, search×2), 412ms
[{"file":"a.go","lines":3},…]
[console]
skip vendor/b.go
```

Failure: `script failed (tool-failed) — 3 calls ran and their effects are real: …` / `script failed (parse) at line 4: SyntaxError: …`. Error kinds are a closed set: `parse | unsupported | unknown-tool | bad-args | tool-failed | limit | timeout | memory | runtime`. `Summary` (TUI/ACP one-liner): `script (7 calls)`.

### Config (one key, three layers resolved like skills)

```jsonc
"codemode": { "enabled": true }     // user config only; the project may set false
```

`resolveCodemode(cfg) CodemodeState{On, Warning, Note}` mirrors `ResolveSelfManagedSkills` (`internal/config/config.go:125-148`): user `true` + project `false` → off with a note; project `true` without user `true` → warning naming the config file. `ProjectConfig` gains `Codemode *bool` (`internal/config/project.go:14`) — a project `true` is declarative, never enabling.

### Cost table (per session)

| Case | Cost |
|---|---|
| codemode off (default) | **0 tokens, 0 bytes of prompt, 0 schema entries.** No new prefix, no cache reset. |
| enabled, idle | 1 tool schema (~90 tokens) + 1 prompt line (~35 tokens) — once per session, cached afterwards |
| enabled, per call | one `tool_use` + one `tool_result` in context: the script in, the capped result out; nested results never enter context |
| enabled, per nested call | 0 model tokens; one pipe round trip; parent-side cost = the tool's own cost (a `shell` still runs a process) |
| disabled at runtime | config is read at start (§4); no mid-session toggle (the prompt is frozen per session, §14) |

## Out of scope (v1)

| Not built | Why | Trigger to revisit |
|---|---|---|
| Async/`Promise.all` nested calls | `Env` is single-goroutine by contract; parallel nested calls need a mutex over run state, and `xargs -P` already covers latency-critical parallelism | a measured N≥20-file task where the sequential loop is the bottleneck |
| `store()` / cross-call state | creates a hidden channel compaction cannot see; moca has files and the session for that | a user report of re-deriving the same index in two scripts |
| `searchTools()` / `ALL_TOOLS` / namespaces | 8 declared tools fit in the schema block; MCP discovery already lives inside the `mcp` schema | a deferred tool catalog (i.e. a different feature) |
| `image()` / `models` | moca has no image or classifier models | such a model surface existing |
| Pi's `codemode.mode: only` (all tool calls through scripts) | rewrites the loop, TUI, ACP and session replay; the model loses the direct call path on tasks where one call is right | PR B's numbers showing the tool wins but is rarely chosen |
| OS-level isolation (bwrap/Landlock/sandbox-exec/Docker) | §16 non-goal, Windows hole, and the child + tool boundary already bounds the blast radius to "what the model could do anyway" | a threat model that includes a hostile *user* on the same host |
| Mid-session toggle (`/codemode`) | the prompt is frozen per session (§14) | never for the prompt slot; a restart is the toggle |
| Windows-specific worker quirks | `SetProcessGroup`/`KillProcessGroup` already branch per platform (`shellrun_windows.go:23-27`); the gate runs on Linux only, as the other gates do | a Windows user report |

## Risks / decisions

| Risk | Mitigation in this plan |
|---|---|
| A wedged VM hangs the agent (regexp2 backtracking, OOM) | the process boundary + hard kill at deadline+2 s (Task 2, `TestHardKillBeatsAWedgedVM`) — the failure mode is a failed script, not a lost session |
| The model never chooses the tool (opt-in tools are invisible in practice) | one prompt line (~35 tokens, enabled only) + a description with two worked examples + the sweep eval that measures adoption (Task 10) |
| A new dependency in a repo that has hand-rolled everything | goja is a leaf-only import, MIT, pure Go, no cgo; the release matrix is unchanged; the alternative (own interpreter, OpenCode's route) is a permanent maintenance cost moca has never taken on |
| Approval fatigue amplification (a loop over ask-tier calls) | `maxApprovals` 10 + `maxToolCalls` 500 + the deadline (R3, `TestApprovalBudget`) |
| Token creep for users who never enable it | conditional registration + the `{{codemode}}` empty slot: **zero** bytes when off, pinned by `TestSchemasFrozen` staying green and the byte-identical prompt test |
| A prompt injection steers a script into exfiltration | no net/fs in the VM; `tools.web` hits the private-host gate, `tools.shell` the ladder; the injected text is data in the script's input, and the result the model sees is script-chosen — the same exposure as the model calling the tools itself, which §11's threat model already owns |
| The child binary changes mid-run (self-update) | the parent holds an open executable; a replaced file is invisible to a running process on Unix; on Windows the spawn fails with a model-facing error |
| A gate that only runs on Linux hides a Windows break | the worker uses only `os/exec` + the already-branched kill helpers; the TUI/ACP changes are pure functions; the risk is recorded, not tested |

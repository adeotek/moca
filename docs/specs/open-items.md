# Open items from the v0.7.0 branch review

> Last updated: 2026-10-19 · source: two review passes over `chore/self-managed-skills-plan` — each pass's fixes landed in the same change that recorded its open items (1–8 from the first, 9–11 from the second; item 5 merges one finding from each)

These are findings the review passes verified but deliberately left unchanged — each needs a policy or design call rather than an obvious one-line fix, or is cosmetic. None blocks the branch. The guard's real holes (the `-C`/`cd` generic-runner bypasses, the named-rule skip, the fold escapes, the dead C5b guard, the same-day ×1 → ×2 bump, the steering-loss on append failure (the messages after the failed one; the second pass re-queues the failed message too); and from the second pass: the kept tail's open tool turn losing its thinking, the resumed guard refusing the frozen prompt's date, a ×2 bump to a date off the host clock, the `--opt=PATH` and after-`cd` writer operands, `Basic`/`Bearer` prose and `${VAR}` URL passwords read as credentials, the shell's skill refusal arming the hint, the hint landing on a purely mutating command) are **fixed and pinned**, not listed here.

For the standing open item on allowlisted interpreters writing skill files (python/node/npm/pytest/docker and friends) — still unapproved but reachable — see SPECS §15's `TestGenericRunnerAllowRules` pin; nothing below re-opens that.

## Open

1. **Bare-word override values still name commands — `permissions` generic-runner guard.** `make test GORUN=bash` passes: `plainMakeValue` accepts any plain alphanumeric word, and a bare word resolved from PATH (or consumed by a recipe variable) can be a command, not data. Distinguishing `VERSION=1.2.3` (inert) from `RUNNER=rm` (code) statically would refuse legitimate word overrides this repo relies on. Needs a fail-closed policy call: either a denylist of recipe-command-looking values, restricting allowed values to numeric/version shapes, or accepting the residual risk and pinning it as a §15-class open item in the probe test.
2. **`rm -rf .moca` (the skills dir's parent) wipes every auto skill unvalidated.** `skillTarget` covers the dir itself and below; the parent is just an in-workdir path, auto-allowed in auto mode for literal operands. Same trust class as any in-workdir `rm`, but the wipe strips the user's accumulated project knowledge in one command; a guard for paths *above* the skills dir (or at least the skills roots) is worth considering.
3. **`hygieneSummary` under-reports when a skill both loses rules and becomes empty.** `PruneAutoSkills` counts removed rules in `RulesRemoved` but names only surviving skills in `Touched`; the summary's count row requires `Touched` non-empty, so removals that emptied a skill leave only "removed empty moca-x". Cosmetic — the print stays truthful; fix is reporting the count even when no skill survived (or a joint clause).
4. **Prune ages anchor to UTC midnights.** `PruneAutoSkills` computes `now.Sub(r.Last)` as elapsed 24 h durations from a date string; in UTC− timezones a rule can be pruned hours before it is 90 local calendar days old, and in UTC+ zones pinned-age notices surface late by the same margin. Sub-day wobble; if calendar-day semantics are the intent, either compare `.Format`-derived calendar dates or leave a comment stating the skew is accepted.
5. **The provenance-change refusal only knows the ×1 → ×2 bump.** Any other provenance change to a stored rule (same rule text) falls through to `validate`'s catch-all refusal in `autoskill.go`, which says "a confirmed rule goes (×1, d) → (×2, today) once" whatever was attempted. Two transitions hit it: a stored rule with absent or undatable provenance can never be given one (`old.HasProv` gates the bump), and the message quotes its zero date as `(×1, 0001-01-01)`; and in a `/remember` run (`UserSignal` set) an existing `(×1, d)` rule cannot become `(user, today)`. The spec does not say whether either transition is allowed, and rewording the rule's text is the only escape today. Decide the allowed transitions (back-filling provenance, pinning an observed rule) and make the refusal name the change that was attempted, together.
6. **ACP `/remember` with the rule only in an attachment errors the whole request.** `textBlocks` correctly excludes resource blocks, so `splitCommand` yields empty args and `Agent.Remember` returns its usage error as the prompt's error result — the TUI prints a usage line instead. Acknowledged in the `server.go` comment; consider mirroring the TUI's per-prompt usage-note shape.
7. **A user template named `remember` shadows differently per surface.** In the TUI the built-in always wins (even with the feature off); in ACP's `expand`, with the feature off the template runs. Cross-surface inconsistency only; pick one precedence and note it in §9/§12.
8. **SPECS §15 test-count drift.** The first pass adds 10 top-level tests (make-guard walk/cd/named pins, the case-variant skill refusal, the multibyte fold pin, the reaching-C5b untrusted-resume guard, the same-day bump, the steering re-queue) and the second pass 5 more (the open-tool-turn thinking, the resumed session date, scheme prose, the hint on mutating commands, the shell refusal not arming it); §15's established-count line should be refreshed at the branch's next bookkeeping pass per house rule (one count update per PR, not per push).
9. **Cold-repo arming accepts any non-inspect command as "how this repo verifies".** `verifies()` deliberately counts everything that is not inspect-only, so in a repo with no skill yet the first successful `go version` or `npm install` arms and delivers the hint. That makes the hint call a setup command the repo's verification procedure. The existing tests use `go version` as the verifying command and `skills-cold` measured the 0/6 → 2/6 trigger on this predicate, so narrowing it (a test/build/lint allowlist, say) changes a measured baseline. It needs a design call and a re-run, not a quiet edit.
10. **The writer-operand refusal also covers source operands.** `cp .moca/skills/moca-go/SKILL.md /tmp/review.md` is refused, because the check does not know which operand is the destination. It errs safe; telling them apart needs a per-tool operand table (`cp -t`, `install -t`, `ln`'s forms, `rsync`), and a wrong table is a new bypass. A source is only read-only for some tools: `cp`, `install` and `ln` leave it alone, but `mv` and `rsync --remove-source-files` delete it, so `mv .moca/skills/moca-x/SKILL.md /tmp/x` removes a skill and must stay refused, and every `rm` operand is a target. So the table has to say, per tool and option, whether the source is written, not just which operand is the destination.
11. **Windows has no shell skill-write refusal.** `checkWindows` never calls `skillTarget`, so `Set-Content .moca\skills\moca-x\SKILL.md …` passes `Check`. That parser is best-effort by design (§7: no PowerShell parser, no quoting model), and the tool-side guard plus the load-time re-validation still hold there. If it is added, it belongs in that parser's own word model.

## Non-goals (recorded, not planned)

- `git apply`, `patch < diff` with the diff from stdin, `rsync` with `--files-from`: a writer whose operand list does not name its targets stays outside the static shell refusal (pattern-level by design); the load-time re-validation backstop drops a contract-breaking result with one warning.
